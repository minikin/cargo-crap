## Part 2: Generic review (code-review skill, medium)

One finding, **resolved** after a user decision (see Part 3):

1. `src/report/types.rs` `cc_display`: integrality is exact
   (`cc.fract() == 0.0`). Once T1 accumulates the weight as `f64`, weights
   that are not exact in binary drift: starting at 1.0, five `?` at 0.2 give
   `1.9999999999999998`, ten at 0.1 give `2.000000000000001`, ten at 0.3 give
   `3.999999999999999`. Each renders `2.0` / `2.0` / `4.0` instead of `2` /
   `4`. Weights 0.5 / 0.25 / 0 / 1 are exact and unaffected. Unreachable on
   this branch (no weighting exists until T1 and T4 land).
   Not applied, because both fixes step outside T2 as approved:
   - a tolerance in `cc_display` (treat `|cc − round(cc)| < 1e-9` as
     integral) contradicts the spec's stated property "non-integral inputs
     render with exactly one decimal digit": it needs a spec amendment;
   - rounding the accumulated CC (e.g. to 1e-9) belongs to T1's counting in
     `src/complexity.rs`, which this task may not edit.
   Proposed: amend the spec to define "integral" up to float noise, then
   apply whichever of the two the user prefers.

## Part 3. Follow-up: the float-drift amendment

The user approved amending the T1 and T2 task lines. On this branch,
`cc_display` now rounds to one decimal and drops a trailing `.0`, so float
noise (`1.9999999999999998` → `2`) and fractions below the display precision
(`2.04` → `2`, `2.96` → `3`) read as the whole number. The old
`cc_display_keeps_the_decimal_when_a_fraction_rounds_to_a_whole` asserted the
opposite (`2.96` → `3.0`) and was replaced by
`cc_display_drops_the_decimal_when_a_fraction_rounds_to_a_whole` and
`cc_display_hides_float_noise_from_a_non_dyadic_weight`. The T1 branch
separately applies the weight once, so the drift no longer arises in the
first place; this is the display-side half.

Spec conformance: the scenario tests are unchanged and still pass (`1.5`,
`3`). Generic review (`code-review` skill, low, over the uncommitted diff):
no findings. Unreachable edge noted, not a defect: `cc_display(-0.0)` renders
`-0`, and CC is never below 1.
